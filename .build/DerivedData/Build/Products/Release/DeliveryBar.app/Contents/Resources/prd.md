# DeliveryBar 产品需求文档 PRD

## 1. 产品概述

### 1.1 产品名称

DeliveryBar

### 1.2 产品定位

DeliveryBar 是一款面向开发者个人使用的 macOS 菜单栏需求管理工具，用于追踪当前正在开发、已开发但未交付、待验收以及已归档的需求状态，帮助开发者避免因为需求排期长、任务过多导致的遗漏、延期和交付遗忘问题。

### 1.3 产品背景

在日常开发过程中，一个开发人员通常会同时处理多个需求。由于需求排期较长、开发周期被打断、临时任务插入、联调和验收时间不确定，容易出现以下问题：

1. 需求开发完成后忘记交付。
2. 已经交付但忘记跟进验收。
3. 需求长期处于开发中，但没有明显提醒。
4. 已完成需求没有及时归档，导致任务列表混乱。
5. 需求状态分散在 Jira、禅道、文档、聊天记录、代码分支中，个人视角下不够直观。

因此，需要一个轻量级、常驻菜单栏的个人需求状态追踪工具，让开发者可以快速查看当前需求状态，并及时处理未完成的交付流程。

---

## 2. 产品目标

### 2.1 核心目标

帮助开发者清晰管理个人负责的需求状态，尤其是防止“开发完但忘了交付”的情况。

### 2.2 具体目标

1. 支持在 macOS 菜单栏中常驻显示。
2. 支持快速查看当前正在开发的需求。
3. 支持查看已开发但未交付的需求。
4. 支持查看待验收、已完成、待归档的需求。
5. 支持对完成需求进行 Archive 归档。
6. 支持对长时间未处理、已开发未交付的需求进行轻量提醒。
7. 支持本地持久化保存需求数据。

---

## 3. 用户群体

### 3.1 目标用户

主要面向软件开发人员，尤其是后端开发、客户端开发、全栈开发、测试开发等需要同时处理多个需求的人群。

### 3.2 用户特征

1. 日常需要处理多个并行需求。
2. 需求交付周期较长。
3. 经常被临时任务打断。
4. 需要跟进开发、联调、验收、上线、归档等多个阶段。
5. 希望有一个轻量、不打扰、不复杂的个人工具。

---

## 4. 使用场景

### 4.1 场景一：查看当前正在开发的需求

用户在开发过程中点击菜单栏图标，快速查看当前进行中的需求，确认自己手上还有哪些任务没有完成。

### 4.2 场景二：开发完成后标记为未交付

用户完成代码开发后，将需求状态从“开发中”修改为“已开发未交付”，提醒自己后续还需要交付、提测或通知相关人员。

### 4.3 场景三：跟进待验收需求

需求已经交付给测试或产品，但还未确认完成。用户可以将其标记为“待验收”，后续持续跟进。

### 4.4 场景四：完成后归档

需求上线或验收完成后，用户将其归档到 Archive，保持当前需求列表简洁。

### 4.5 场景五：超时提醒

如果某个需求处于“已开发未交付”状态超过指定天数，菜单栏和列表中会出现明显提示；后续版本可进一步弹出本地通知提醒用户处理。

## 5. 功能需求

## 5.1 菜单栏常驻入口

### 功能描述

应用启动后，在 macOS 顶部菜单栏显示常驻图标。用户点击图标后弹出需求面板。

### 功能规则

1. 菜单栏必须常驻显示应用图标。
2. 点击菜单栏图标后展示需求列表面板。
3. 面板支持查看不同状态下的需求。
4. 面板中提供新增需求、编辑需求、归档需求等操作入口。
5. 第一版默认作为菜单栏应用使用，不展示主窗口；是否隐藏 Dock 图标可作为后续设置项。
6. 面板宽度建议控制在 360 到 420 pt，高度随内容增长但不超过屏幕可用高度。
7. 当存在超时未处理需求时，可在菜单栏图标旁展示数量、红点或高亮状态，但不能替代应用图标。
8. 无需求时展示空状态，并提供“新增需求”入口。

### 优先级

P0

---

## 5.2 需求新增

### 功能描述

用户可以手动新增一个需求，用于记录自己当前需要处理的开发任务。

### 字段设计

| 字段     | 说明        | 是否必填 |
| ------ | --------- | ---- |
| 需求名称   | 需求标题      | 是    |
| 需求描述   | 需求详细说明    | 否    |
| 当前状态   | 需求当前阶段    | 是    |
| 优先级    | 高 / 中 / 低 | 否    |
| 负责人    | 默认本人      | 否    |
| 预计交付时间 | 计划完成时间    | 否    |
| 备注     | 补充说明      | 否    |
| 创建时间   | 系统自动生成    | 是    |
| 更新时间   | 系统自动更新    | 是    |

### 优先级

P0

---

## 5.3 需求状态管理

### 功能描述

用户可以根据需求进展修改状态。

### 状态枚举

| 状态   | 说明                 |
| ---- | ------------------ |
| 待开发  | 已记录但还未开始           |
| 开发中  | 正在编码实现             |
| 已开发未交付 | 代码开发完成，但还未提测、交付或通知 |
| 待验收  | 已交付，等待测试、产品或相关方确认  |
| 已完成  | 需求已完成，等待归档          |
| 已归档  | 不再展示在主列表中           |

### 推荐流转

```text
待开发 → 开发中 → 已开发未交付 → 待验收 → 已完成 → 已归档
```

### 功能规则

1. 用户可以手动修改任意状态。
2. 每次修改状态后自动更新“更新时间”。
3. 已归档需求默认不展示在主列表中。
4. 用户可以进入 Archive 页面查看历史需求。
5. 修改状态时记录“状态变更时间”，提醒规则优先基于状态变更时间计算。
6. 第一版不增加“待上线”状态，避免状态过细导致维护成本上升。

### 优先级

P0

---

## 5.4 需求分组展示

### 功能描述

在菜单栏面板中，按照需求状态进行分组展示。

### 分组规则

默认展示以下分组：

1. 待开发
2. 正在开发
3. 已开发，未交付
4. 待验收
5. 已完成

Archive 作为独立入口展示，不默认混在主列表中。

### 展示内容

每条需求展示：

1. 需求名称
2. 当前状态
3. 优先级
4. 距离上次更新的时间
5. 预计交付时间
6. 快捷操作按钮
7. 超时标记，例如“3 天未交付”“7 天未推进”

### 优先级

P0

---

## 5.5 需求编辑

### 功能描述

用户可以编辑已有需求的信息。

### 可编辑字段

1. 需求名称
2. 需求描述
3. 当前状态
4. 优先级
5. 预计交付时间
6. 备注

### 功能规则

1. 编辑保存后自动更新“更新时间”。
2. 需求名称不能为空。
3. 修改状态时记录状态变更时间。
4. 仅修改备注、描述等普通字段时，不应影响状态变更时间。

### 优先级

P0

---

## 5.6 需求删除

### 功能描述

用户可以删除不需要继续跟踪的需求。

### 功能规则

1. 删除前需要二次确认。
2. 删除后本地数据移除。
3. 第一版可以做物理删除，后续版本可改为回收站。

### 优先级

P0

---

## 5.7 需求归档 Archive

### 功能描述

用户可以将已完成需求归档，避免主列表过于混乱。

### 功能规则

1. 归档后的需求进入 Archive 页面。
2. 主列表默认不展示 Archive 需求。
3. Archive 中的需求可以恢复到其他状态。
4. 归档时记录归档时间。

### 优先级

P0

---

## 5.8 超时提示与本地提醒

### 功能描述

系统根据需求状态和状态变更时间，对用户进行轻量提示或本地通知提醒。

### 提醒规则

默认提醒规则：

1. “已开发未交付”超过 3 天未处理，提醒用户。
2. “开发中”超过 7 天未推进，提醒用户。
3. “待验收”超过 5 天未处理，提醒用户。
4. 到达预计交付时间当天，提醒用户。

V1.0 使用菜单栏数字、高亮和列表内超时文案作为轻量提示；V1.1 再接入 macOS 本地通知。

### 提醒文案示例

```text
需求「司机证件审核规则优化」已经开发完成 3 天，但还未交付。
```

```text
需求「声纹风控策略接入」已经开发 7 天，请确认是否需要推进或拆分。
```

### 功能规则

1. 用户可以开启或关闭提醒。
2. 第一版可以使用默认提醒规则。
3. 后续版本支持用户自定义提醒时间。
4. 同一需求同一提醒类型一天内最多提醒一次。
5. 用户修改状态后，当前状态下的提醒计时重新开始。
6. 用户可以通过“稍后提醒”临时隐藏某条需求的提醒。

### 优先级

P0（菜单栏与列表内超时提示）/ P1（系统本地通知）

---

## 5.9 本地数据存储

### 功能描述

所有需求数据保存在本地，应用重启后数据不丢失。

### 技术方案

使用 SwiftData 进行本地数据持久化。

### 存储对象

Requirement：

| 字段         | 类型     | 说明      |
| ---------- | ------ | ------- |
| id         | UUID   | 需求唯一 ID |
| title      | String | 需求名称    |
| detail     | String | 需求描述    |
| note       | String | 备注      |
| status     | Enum   | 当前状态    |
| priority   | Int    | 优先级     |
| owner      | String | 负责人     |
| createdAt  | Date   | 创建时间    |
| updatedAt  | Date   | 更新时间    |
| statusChangedAt | Date | 状态变更时间 |
| dueDate    | Date?  | 预计交付时间  |
| completedAt | Date? | 完成时间    |
| archivedAt | Date?  | 归档时间    |
| lastRemindedAt | Date? | 上次提醒时间 |
| reminderMutedUntil | Date? | 临时隐藏提醒到期时间 |

### 优先级

P0

---

## 5.10 开机自启动

### 功能描述

用户可以设置应用开机后自动启动。

### 功能规则

1. 默认不开启开机自启动。
2. 设置页中提供开关。
3. 用户开启后，系统登录时自动启动 DeliveryBar。
4. 该功能不进入 V1.0，避免第一版被系统权限和签名配置阻塞。

### 优先级

P2

## 6. 非功能需求

### 6.1 性能要求

1. 应用启动时间小于 2 秒。
2. 菜单栏面板打开无明显卡顿。
3. 本地需求数量在 1000 条以内时，列表展示流畅。
4. 内存占用尽量保持轻量。

### 6.2 稳定性要求

1. 应用异常退出后，本地数据不能丢失。
2. 数据保存失败时需要提示用户。
3. 编辑需求时避免因为窗口关闭导致数据丢失。

### 6.3 易用性要求

1. 新增需求步骤不超过 2 步。
2. 修改需求状态尽量通过快捷按钮完成。
3. 菜单栏面板信息要简洁，避免做成复杂项目管理系统。
4. 核心状态一眼可见。

### 6.4 隐私要求

1. 第一版所有数据仅保存在本地。
2. 不上传用户需求数据。
3. 不需要账号登录。
4. 不接入第三方分析 SDK。

```swift
enum RequirementStatus: String, Codable, CaseIterable {
```

```swift
enum RequirementPriority: Int, Codable, CaseIterable {
```

## 11. 验收标准

### 11.1 V1.0 验收标准

1. 应用启动后能在 macOS 菜单栏显示图标。
2. 点击菜单栏图标后能打开需求面板。
3. 用户可以新增需求。
4. 用户可以编辑需求。
5. 用户可以删除需求。
6. 用户可以修改需求状态。
7. 需求可以按照状态分组展示。
8. 用户可以将需求归档。
9. 应用关闭并重新打开后，需求数据仍然存在。
10. Archive 需求可以单独查看。
11. 已开发未交付超过 3 天、开发中超过 7 天、待验收超过 5 天的需求在列表中有明显超时标记。
12. 菜单栏始终展示应用图标，并可展示未处理或超时需求数量。
13. 修改备注或描述不会重置状态超时计时。

### 11.2 V1.1 验收标准

1. 已开发未交付需求超过 3 天后可以触发提醒。
2. 开发中需求超过 7 天未推进后可以触发提醒。
3. 待验收需求超过 5 天未处理后可以触发提醒。
4. 用户可以开启或关闭提醒。
5. 未授权通知时，应用能引导用户开启权限或继续使用列表内提示。
6. 同一需求同一提醒类型一天内不会重复弹出多次。

## 12. 风险与注意事项

### 12.1 产品风险

1. 功能过多后可能变成复杂项目管理工具，违背轻量化定位。
2. 用户手动维护成本过高，可能导致不愿意持续使用。
3. 如果状态流转过细，会增加使用负担。

### 12.2 技术风险

1. 菜单栏窗口尺寸较小，信息展示需要克制。
2. SwiftData 数据模型后期变更需要考虑迁移。
3. macOS 本地通知需要用户授权。
4. 开机启动需要处理系统权限和设置。

### 12.3 解决策略

1. 第一版只做核心状态管理和轻量超时提示。
2. 优先减少用户输入成本。
3. 状态控制在 5 到 6 个以内。
4. 所有复杂功能放到后续版本。
5. 本地存储优先，不做账号系统。

---

## 13. 总结

DeliveryBar 的核心价值是帮助开发者追踪个人负责需求的交付状态，尤其是解决“开发完成但忘记交付、验收、归档”的问题。

第一版应保持轻量，只围绕以下核心流程设计：

```text
记录需求 → 开发中 → 已开发未交付 → 待验收 → 已完成 → 已归档
```

产品不应定位为 Jira、禅道或 Tapd 的替代品，而应该定位为开发者个人使用的菜单栏需求提醒工具。
